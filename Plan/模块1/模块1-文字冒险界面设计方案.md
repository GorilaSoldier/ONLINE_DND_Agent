# 模块1：文字冒险界面设计方案

**文档版本**：v2.6
**编写日期**：2026-07-27
**更新日期**：2026-07-31（历史消息累积替代贴文本；开场白 AI 预生成；任务面板 JSON 驱动 + 点击交互；两个已知问题记录）
**所属模块**：模块1 - 前端多端交互与沉浸式界面模块

---

## 1. 概述

### 1.1 设计目标

为 DNDBOX 的非战斗阶段提供贴合线下跑团体验的交互界面。玩家通过自由文本输入宣告动作，由 AI GM 或真人 GM 根据当前剧本章节、地点状态和角色能力进行裁定与叙事推进。

界面核心不再是「空间网格探索」，而是：

> **GM 描述场景 → 玩家自由输入动作 → 系统/AI 裁定并更新世界状态 → 叙事日志追加结果**

### 1.2 核心设计理念

| 要素 | 设计 |
|------|------|
| **叙事** | 中央为可滚动叙事日志，按时间顺序展示 GM 描述、玩家动作、检定结果、NPC 对话 |
| **输入** | 日志下方为自由文本输入框，玩家输入想说或想做的事 |
| **上下文** | 左侧面板展示当前地点的可见 NPC、物品、出口；点击可查看详细描述 |
| **角色** | 右侧面板展示完整角色卡，含属性、技能、背包、法术 |
| **数据** | 全 JSON 驱动，剧本分章节，AI/规则引擎只读取当前章节相关数据 |
| **约束** | AI GM 受硬规则约束，不能引入当前上下文之外的 NPC、地点、物品或剧情 |

### 1.3 页面定位

- 文件：`adventure.html`（独立页面）
- 复用 lobby.html 的色彩体系（CSS 变量）
- 从 lobby.html 点击"开始冒险"跳转进入，携带剧本 ID 与章节 ID 参数

## 2. 整体布局（三栏）

```
┌────────────────────────────────────────────────────────────┐
│  [返回大厅]                    DNDBOX                       │  ← top-bar
├────────────────────────────────────────────────────────────┤
│  左侧面板  │           中央区域             │   右侧面板    │
│           │  ┌─────────────────────────┐  │               │
│ 当前地点   │  │   📍 石丘旅馆 · 大厅     │  │   角色卡       │
│ ├ 人物    │  ├─────────────────────────┤  │   属性/技能    │
│ ├ 物品    │  │                         │  │   背包/法术    │
│ ├ 出口    │  │     narrative-log       │  │               │
│           │  │     (可滚动叙事日志)      │  │   侦察 / 调查   │
│ 队伍成员   │  │                         │  │   快捷检定按钮  │
│ 当前任务   │  │  GM：石丘旅馆的大厅里...  │  │               │
│           │  │  玩家：我想...             │  └───────────────┘
│           │  │  GM：请进行...             │
│           │  │                         │
│           │  └─────────────────────────┘
│           │  [我想说/想做 __________] [发送]
└───────────┴───────────────────────────────┴────────────────┘
```

### 2.1 顶部栏

- 左侧：返回大厅按钮
- 中央：DNDBOX 品牌

### 2.2 中央区域

中央区域是核心交互区，包含：

#### 2.2.1 地点标题

- 显示当前地点名称，如 `石丘旅馆 · 大厅`
- 若剧本有设定当前时间、天气或章节，可在标题下方以小字显示；无设定则不显示
- 进入新地点时自动更新

#### 2.2.2 叙事日志（narrative-log）

- 带垂直滚动条的文本区域
- 按时间顺序追加消息条目
- 每条消息标注角色/来源，如 `GM:`、`玩家:`、`系统:`
- 不添加 emoji，纯文字呈现
- 新消息自动滚动到底部
- 消息类型：
  - GM 场景描述
  - 玩家输入的动作
  - 检定请求与结果
  - NPC 对话
  - 被动技能触发提示
  - 状态变化提示（获得/失去物品、NPC 态度变化等）

#### 2.2.3 输入区

- 单行或少量行文本输入框
- 提示文字：`我想说/想做...`
- 发送按钮
- 支持回车发送
- 输入框上方不放固定快捷按钮（侦察/调查放到右侧面板角色卡附近）

### 2.3 左侧面板：当前场景上下文

左侧面板显示玩家角色当前能感知到的事物，定位为"你已注意到的事物"，不是可交互白名单。玩家仍可输入面板未列出动作。

#### 2.3.1 当前地点

- 地点名称
- 点击地点名称：弹出地点详细描述框

#### 2.3.2 人物

- 当前在场的 NPC 列表
- 每个 NPC 显示：名称 + 简短身份
- 点击 NPC：弹出描述框，显示完整介绍、当前状态、可见信息
- 描述框内可继续输入与该 NPC 相关的动作

#### 2.3.3 物品

- 当前地点中可见的物品列表
- 点击物品：弹出描述框，显示物品描述、主人（若有）、是否可拾取/偷窃

#### 2.3.4 出口

- 当前地点可通往的其他地点
- 点击出口：弹出描述框，显示出口描述，或自动在输入框填入移动动作草稿

#### 2.3.5 当前任务

- 从 quests.json 加载，仅显示 `status === 'active'` 的任务
- 点击任务展开子任务列表（仅显示已完成 + 第一个未完成，防剧透）
- 点击子任务弹出详情模态框（左侧分类 + 右侧阶段目标 + SVG 勾选框）
- 全部子任务完成后任务从侧边栏消失

### 2.4 右侧面板：完整角色卡

右侧面板展示完整角色信息：

- 头像、名称、种族、职业、等级
- 属性值（力量、敏捷、体质、智力、感知、魅力）
- 技能列表（可点击发起检定）
- 豁免检定
- HP / AC / 先攻 / 速度
- 背包
- 法术位和已知法术

#### 2.4.1 侦察 / 调查快捷按钮

在角色卡附近放置两个常用检定按钮：

- **侦察**：触发感知（Perception）检定，查看周围环境
- **调查**：触发调查（Investigation）检定，仔细检查某个区域或物品

点击后系统自动发送对应动作并掷骰。

### 2.5 拖拽把手

- 保留左/右面板的拖拽调整宽度
- 宽度持久化到 localStorage
- 恢复时保证中央区域最小宽度

## 3. 交互模型

### 3.1 核心循环

```
GM 描述当前场景
    ↓
玩家阅读后在输入框输入动作
    ↓
后端意图识别（对玩家透明）
    ↓
规则引擎判断是否需要检定、目标是否合法
    ↓
后端自动掷骰
    ↓
AI GM / 真人 GM 根据结果生成叙事回复
    ↓
更新世界状态（物品、NPC、玩家状态）
    ↓
叙事日志追加结果
```

### 3.2 玩家输入示例

```
GM：石丘旅馆的大厅里壁炉噼啪作响。托布拉·石丘正在吧台后擦杯子，
    弗雷达·矿工坐在角落。吧台后面挂着一串客房钥匙。

玩家：我想趁托布拉不注意，偷走那把钥匙串。

系统：请进行巧手（Sleight of Hand）检定，难度 12。

[后端自动掷骰：d20 + 加值 = 14]

GM：你借着桌子的掩护，手指轻巧地勾住了钥匙串。托布拉仍在擦杯子，
    完全没有注意到。你获得了：客房钥匙串。
```

### 3.3 输入辅助

左侧面板的 NPC、物品、出口可点击，点击后弹出详细描述框。当前阶段不实现"点击后自动填充输入框"的快速选择功能，后续可扩展。

### 4.2 可见信息

- 地点描述、NPC、物品、出口默认对进入该地点的玩家可见
- 不单独设置"显眼物品"分类

### 4.3 隐藏信息

- 由 `hidden` 字段定义
- 需要玩家主动侦察/调查，或被动技能满足 DC 才能发现
- 剧本未写隐藏信息时，不硬加

### 4.4 场景节点

- 预置的触发式叙事片段
- 当玩家满足触发条件时，GM 叙事中自然插入
- 用于控制剧情节奏和关键信息释放

## 5. NPC 系统

### 5.1 NPC 数据

NPC 需要足够完整的设定，AI 才能保持一致发挥：

```jsonc

    "id": "toblen-stonehill",
    "name": "托布拉·石丘",
    "race": "矮人",

    "description": "一位面容和蔼的矮人旅馆老板...",
    "personality": ["谨慎", "好客", "护短"],
    "goals": ["保护旅馆和家人", "赚足够的钱"],
    "fears": ["红标帮", "失去旅馆"],

    }
  }

```

### 5.2 NPC 状态

运行时 NPC 维护以下状态：

```js
{
  awareness: "unaware",    // unaware | suspicious | alert | hostile
  attitude: "neutral",     // friendly | neutral | hostile
  current_location: "stonehill-inn-hall",
  can_see_player: true,
  memory: [
    { event: "theft_attempt_detected", timestamp: 123456 }
  ]
}
```

### 5.3 NPC 反应流程

1. 玩家动作触发 NPC 相关事件
2. 规则引擎根据事件类型、NPC 性格、当前状态选择反应模板级别
3. AI GM 在模板基础上根据性格、记忆、当前情境润色
4. 更新 NPC 状态

### 5.4 延迟发现

偷窃成功后，根据物品显眼程度和 NPC 细心程度决定是否延迟发现：

- `notice_chance` 决定是否最终会发现
- `notice_after` 决定发现时间范围
- 发现后触发新的 NPC 反应事件
- 若剧本未写，默认不延迟发现

## 6. 玩家角色与技能

### 6.1 角色卡

右侧面板展示完整角色卡，数据来自 `localStorage.currentCharacter` 或后端角色数据。

### 6.2 常用检定

角色卡附近放置两个最常用检定按钮：

- **侦察**：发起感知（Perception）检定
- **调查**：发起调查（Investigation）检定

所有技能检定也可通过角色卡中的技能列表点击触发。

### 6.3 被动技能

当玩家进入地点或发生事件时，后端自动用被动技能比对隐藏信息 DC：

- 被动察觉 ≥ DC：自动发现，GM 叙事中追加
- 被动洞悉 ≥ DC：自动察觉 NPC 隐瞒或说谎
- 被动调查 ≥ DC：自动发现异常装置或机关

被动发现的结果以简洁方式插入叙事，避免叙事过于碎片化。

## 7. AI GM 架构

### 7.1 模式

支持三种模式，可在冒险过程中切换：

| 模式 | 说明 | 当前状态 |
|------|------|----------|
| 单人 AI 模式 | AI 完全主持，无真人 GM | **已实现**，接入 DeepSeek-V4-Flash |
| AI 辅助 GM 模式 | 真人 GM 在线，玩家输入先到 GM 面板，AI 生成建议回复，GM 可一键采用或修改 | 待实现 |
| 纯真人 GM 模式 | AI 只负责状态管理和检定，回复完全由真人 GM 撰写 | 待实现 |

当前单人 AI 模式实现细节：

- **模型**：`deepseek-v4-flash`
- **API 端点**：`https://api.deepseek.com/v1`（兼容 OpenAI ChatCompletions）
- **配置文件**：`backend/.env` 中配置 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`、`DEEPSEEK_BASE_URL`
- **实现文件**：`backend/services/ai_gm.py`、`backend/routers/game.py`
- **调用方式**：Tool Calling（Function Calling），仅保留流式端点 `/api/game/action/stream`
  1. `chat_with_tools()`：AI 判断是否需要调用后端 `process_action` 工具（流式 SSE 直通，不预收集）
     - 纯对话/闲聊：AI 直接流式回复（1 次 API 调用，首 token 2-3s）
     - 需要状态变更/检定：AI 返回 tool_call 参数 → 规则引擎执行 → `narrate_with_result()` 流式叙事（2 次 API）
  2. 旧版 `interpret()` + `narrate()` **已删除**，旧端点 `/api/game/action` **已删除**
- **降级机制**：AI 调用失败或 API 不可用时，回退到规则引擎模板回复
- **上下文管理（消息累积）**：
  - 每轮对话不再仅保留最近 4 轮文字，而是将 `state.history` 全部转为标准 API messages 格式（user/assistant），累积追加到请求数组末尾
  - Messages 结构：`[system_prompt, opening_exchange, 历史消息逐轮累积..., current_user_prompt]`
  - 随对话增加 token 自然增长，后续需实现超限裁剪/摘要策略
  - 首轮：`chapter_summary` + 完整场景上下文 + NPC 性格/秘密/目标 + 物品/出口（~2000 chars）
  - 后续轮次：场景锚点（`【当前场景】绝冬城受命 — 矿业公会`）+ 玩家输入（~500 chars），历史对话通过 messages 累积传递
  - AI 思考模式 `reasoning_content` 自动捕获并回传，防止 API 400 错误
  - 切换地点/场景时触发完整上下文重发
- **开场白 AI 预生成**：
  - 后端启动时调用 AI 生成开场叙事（非 TC 调用，纯文本生成），缓存到内存
  - 前端 initGame 时调用 `/api/game/opening` 获取，秒级响应（刷新页面直接读缓存）
  - 开场白背景 exchange 注入 session，作为固定消息参与后续每轮对话，替代首轮重复发送 full context
  - System prompt 禁止 AI 介绍玩家角色身份（玩家已知道自己的角色）
- **技能检定**：全部 D&D 技能已覆盖（侦察、调查、洞悉、隐匿、游说、欺瞒、威吓、巧手、运动、体操等 18 项），TC prompt 中明确各技能触发条件，前端显示中文技能名 + 掷骰结果
- **流式输出**：`chat_with_tools` 在 `StreamingResponse` 内部消费，DeepSeek 每吐一个 token 立即以 SSE 事件发给前端，不再预收集后批量发送

### 7.2 AI 约束

通过以下方式防止 AI 幻觉：

1. **System prompt 硬约束**：`_tc_system_prompt`（439 chars）明确 AI 是 GM 角色，只能基于提供的上下文生成回复，禁止引入未提及的 NPC、地点、物品、剧情。
2. **场景锚点防失忆**：增量轮次发送 `【当前场景】绝冬城受命 — 矿业公会` + 地点描述首句作为锚点，防止 AI 在多轮对话后遗忘场景位置和剧情进度。
3. **首轮完整剧情注入**：`_tc_full_user_prompt` 首行发送 `chapter_summary`（~950 chars），包含章节目标、主要地点、关键 NPC、关键物品、关键任务、GM 提示。
4. **NPC 深层信息暴露**：`_tc_full_user_prompt` 的 NPC 展示包含 `id`、`性格`、`秘密（NPC 会隐瞒）`、`目标`，让 AI 能正确角色扮演而非暴露秘密。
5. **ID 精确匹配**：NPC 格式为 `id=gundren-rockseeker，甘德伦·碎石者`，物品格式为 `id=supplies-neverwinter，绝冬城补给箱（可偷窃）`，AI 调用 tool 时必须使用 id=
6. **剧本分章读取**：只把当前章节内容和必要的前置背景喂给 AI，禁止 AI 读取后续章节。
7. **地点/章节边界检查**：若玩家试图前往未解锁地点或触发跨章剧情，GM 应拒绝或引导回当前场景。
8. **AI 输出为自然语言**：不强制结构化输出，保持叙事自由感；规则引擎从 tool_call 参数提取意图，AI 从 tool_result 提取真实掷骰结果后叙事。
9. **状态变化双重维护**：后端 JSON 状态（物品归属、NPC 状态）由 StateManager 管理；剧情记忆（任务进度、对话上下文）由 AI messages 数组维护。首轮注入后不需要每轮重发。

### 7.3 规则引擎

AI 负责叙事生成，后端规则引擎负责校验。Tool Calling 模式下，AI 通过 `process_action` 工具将意图参数传递给规则引擎：

- 目标是否存在
- 动作是否允许（如物品是否可偷窃）
- 是否需要检定
- 检定 DC 是多少
- 掷骰结果
- 状态变化是否合法

支持的意图：talk、move、advance_scene、perception、investigation、steal、look、take、trade、use_item、combat、other。

检定支持的全部技能（18 项）：perception、investigation、insight、stealth、persuasion、deception、intimidation、sleight_of_hand、athletics、acrobatics、arcana、history、nature、religion、medicine、survival、animal_handling、performance。TC prompt 中明确各技能触发条件（如"洞悉/察言观色"→insight，"威吓/恐吓"→intimidation）。

规则引擎执行结果通过 tool result 返回给 AI，AI 基于真实结果生成回复——不会出现"AI 描述了成功偷窃但规则引擎说不允许"的矛盾。

### 7.4 状态持久化

当前开发阶段使用**内存会话存储**，会话 ID 由后端生成并通过 API 返回给前端：

- 运行时状态保存在 `GameState` 实例中（`backend/services/game_state.py`）
- 状态变更由 `StateManager` 统一执行（`backend/services/state_manager.py`）
- 每次动作返回 `updates` 字段，前端根据它刷新 UI

后续将补充持久化：

- `data/adventures/{adventure_id}/sessions/session-{id}.json`：地点物品、NPC 状态、玩家背包、任务进度、事件队列
- `data/adventures/{adventure_id}/sessions/session-{id}-log.md`：叙事日志与 GM 笔记，作为后续 AI 加载的上下文

### 7.5 骰子

- 后端实现自动掷骰引擎
- 支持 `1d20+4`、`2d6`、`8d6` 等表达式
- 支持优势/劣势
- 前端先不做动画，后续补充

## 9. 数据流

```
adventure.html 加载
  │
  ├─ 读取 URL 参数：剧本 ID、章节 ID
  │
  ├─ fetch /data/adventures/{adventure_id}/...
  │   └─ 合并全局 NPC 与章节 NPC，合并装备模板与章节物品
  │
  ├─ 渲染界面
  │   ├─ 中央 narrative-log（初始 GM 描述）
  │   ├─ 左侧面板：当前地点 NPC / 物品 / 出口（后端 /api/game/action 返回初始上下文）
  │   └─ 右侧面板：完整角色卡
  │
  └─ 玩家输入（流式 SSE）
      ├─ 前端追加玩家输入到 narrative-log，显示"正在进行检定..."或"GM 正在思考..."
      ├─ POST /api/game/action/stream（SSE，唯一端点）
      │   ├─ 首轮：发送 chapter_summary + 完整上下文（NPC性格/秘密/目标 + 物品/出口 + 角色）
      │   ├─ 后续轮次：场景锚点 + 最近对话 + 玩家输入（~700 chars）
      │   ├─ AI 判断是否需要 tool_call（流式 SSE 直通，不预收集）
      │   │   ├─ 不需要（纯对话）→ 直接流式输出叙事，逐 token 到达前端
      │   │   └─ 需要 → meta 事件先发检定结果 → 规则引擎执行 → narrate_with_result 流式叙事
      │   └─ 切换地点/场景 → 重发完整上下文
      │
      ├─ 前端逐 chunk 追加 GM 回复到 narrative-log（而非全量替换）
      ├─ meta 事件到达时先展示检定结果（中文技能名 + d20 + 修正 + DC + 成功/失败）
      ├─ meta 事件更新 state_changes / updates（物品增减、地点切换、NPC 状态）
      └─ 清空输入框
```

## 11. 设计决策记录

| 决策 | 原因 |
|------|------|
| 取消 7×7 网格导航 | 网格导航更像单机探索游戏，限制了玩家自由宣告动作 |
| 采用 narrative-log + 输入框 | 更贴近线下跑团 GM-玩家对话循环 |
| 左侧面板只显示可见 NPC/物品/出口 | 提供上下文，但不限制玩家自由发挥 |
| 隐藏信息由剧本决定，不硬加 | 避免无意义填充，保证叙事质量 |
| AI 输出自然语言，规则引擎校验 | 保留叙事自由感，同时防止幻觉和非法状态变化 |
| 剧本分章读取 | 控制 AI 上下文范围，防止剧透和跨章跳跃 |
| 不强制结构化输出 | 自由叙事更符合跑团氛围 |
| 偷窃延迟发现由数据驱动 | 在真实感和可控性之间取得平衡 |
| 场景描述中明确提到的物品视为存在 | 贴合线下跑团高自由度，避免 AI 否认场景内可交互对象 |
| 物品/NPC 归属由地点引用而非物品自标记 | 物品和 NPC 模板是独立的，不需要在模板上标记 location。作者只需在地点 JSON 的 `items`/`npcs` 数组中添加引用即可，新增地点不增加物品维护成本 |
| 约束校验链路（地点→可见物品→AI上下文） | AI 只能看到当前地点引用的物品，自动防止"全局物品幻觉"。校验链路：`location.items → get_context_items() → valid_items → _validate_intent_against_context()` |
| Tool Calling 替代两轮 API 调用 | AI 自主判断是否需要后端：纯对话 1 次调用秒回，需要状态变更时才走工具调用 + 第二轮叙事。相比之前每次都强制 interpret+narrate 两轮，显著降低延迟和 token 消耗 |
| 上下文增量发送，首轮完整后续轻量 | messages 数组天然是 AI 的记忆。首轮发送完整场景上下文+chapter_summary+NPC深层信息，AI 之后的回复里已包含场景信息，后续只需发场景锚点+最近对话+玩家输入。切换地点/场景时重发完整上下文 |
| 技能检定自动掷骰 + AI 基于结果叙事 | AI 通过 process_action 传递意图和目标，规则引擎真实掷骰，tool result 返回真实数据。AI 拿到 `{"checks":[{"roll":14,"success":true}]}` 后叙事——不会出现"AI 描述了成功但规则引擎说不允许"的矛盾 |
| NPC 性格/秘密/目标注入上下文 | AI 需要了解 NPC 的深层设定才能正确角色扮演。性格影响回复风格，目标影响行为动机，秘密是 NPC 极力隐瞒的事——被追问时要含糊其辞或转移话题 |
| chapter_summary 首轮注入 | summary.md 包含章节目标、主要地点、关键 NPC/物品/任务、GM 提示。AI 需要知道"整章剧情应该怎么推进"才能做出符合剧本的回复。因内容固定不频繁变化，只需首轮注入 |
| 增量轮次场景锚点 | 24 chars 的纯增量 prompt 导致 AI "失忆"后编造剧情。加入 `【当前场景】绝冬城受命 — 矿业公会` + 地点描述首句（~130 chars）作为锚点，占完整上下文 17% 但能有效防幻觉 |
| SSE 流式直通而非预收集 | chat_with_tools 从 DeepSeek 实时接收 tokens，之前因在 StreamingResponse 外部消费导致预收集后批量发送。改为在 StreamingResponse 生成器内部消费，每个 token 立即以 SSE 事件下发，首 token 到达时间从 6s 缩短到 2s |
| 旧 interpret+narrate 端点删除 | 旧端点每轮 2 次 API 调用（非流式 interpret + 非流式 narrate），interpret system prompt 达 2,015 chars 纯规则冗余。统一到 TC 架构后删除约 720 行旧代码，system prompt 从 2,844 chars 压缩到 439 chars |
| DeepSeek V4 Flash 思考模式处理 | Tool call 场景下模型自动输出 `reasoning_content`，若第 2 次 API 不回传则报 400。chat_with_tools 自动捕获 reasoning_content 并通过 narrate_with_result 回传。思考模式对意图判断有帮助，占延迟比重极小（<5%），不关闭 |
| 历史消息累积替代"贴文本" | 旧方案每轮 messages 全新构建，"最近 4 轮历史"作为纯文本贴入 user_prompt。4 轮之前的信息全部丢失，NPC 状态变化、对话上下文被遗忘。改为 state.history 全部转为标准 API messages 逐轮累积追加，AI 真正拥有完整对话记忆 |
| 开场白 AI 预生成 | 旧方案硬编码 `location.scene_text` 作为开场，无前因后果。改为后端启动时调用 AI 生成开场叙事并缓存，前端加载时秒级获取。开场白背景 exchange 注入 session，后续每轮作为固定消息参与对话，替代首轮重复发送 full context |
| 任务面板 JSON 驱动 + 防剧透 | 任务从 quests.json 加载，仅显示 `status === 'active'` 的任务。点击任务展开子任务，仅显示已完成子任务 + 第一个未完成子任务（防止剧透后续步骤）。点击子任务弹出详情模态框（参照 lobby.html 风格）。完成任务从侧边栏消失。`find-gundren` 等伏击后才触发的任务初始 status 设为 hidden |
