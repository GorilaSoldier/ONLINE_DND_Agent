# 模块1：文字冒险界面设计方案

**文档版本**：v2.2
**编写日期**：2026-07-27
**更新日期**：2026-07-30（接入 DeepSeek-V4-Flash AI GM，完成物品可见性/隐藏发现机制）
**所属模块**：模块1 - 前端多端交互与沉浸式界面模块

---

## 1. 概述

### 1.1 设计目标

为 DNDBOX 的非战斗阶段提供贴合线下跑团体验的交互界面。玩家通过自由文本输入宣告动作，由 AI GM 或真人 GM 根据当前剧本章节、地点状态和角色能力进行裁定与叙事推进。

界面核心不再是「空间网格探索」，而是：

> **GM 描述场景 → 玩家自由输入动作 → 系统/AI 裁定并更新世界状态 → 叙事日志追加结果**

### 1.2 核心设计理念

| 要素 | 设计 |
|------|------|
| **叙事** | 中央为可滚动叙事日志，按时间顺序展示 GM 描述、玩家动作、检定结果、NPC 对话 |
| **输入** | 日志下方为自由文本输入框，玩家输入想说或想做的事 |
| **上下文** | 左侧面板展示当前地点的可见 NPC、物品、出口；点击可查看详细描述 |
| **角色** | 右侧面板展示完整角色卡，含属性、技能、背包、法术 |
| **数据** | 全 JSON 驱动，剧本分章节，AI/规则引擎只读取当前章节相关数据 |
| **约束** | AI GM 受硬规则约束，不能引入当前上下文之外的 NPC、地点、物品或剧情 |

### 1.3 页面定位

- 文件：`adventure.html`（独立页面）
- 复用 lobby.html 的色彩体系（CSS 变量）
- 从 lobby.html 点击"开始冒险"跳转进入，携带剧本 ID 与章节 ID 参数

│ ├ 出口    │  │     narrative-log       │  │               │
│           │  │     (可滚动叙事日志)      │  │   侦察 / 调查   │
│ 队伍成员   │  │                         │  │   快捷检定按钮  │

│           │  │  GM：请进行...             │

### 2.1 顶部栏

- 左侧：返回大厅按钮
- 中央：DNDBOX 品牌

### 2.2 中央区域

中央区域是核心交互区，包含：

#### 2.2.1 地点标题

- 显示当前地点名称，如 `石丘旅馆 · 大厅`
- 若剧本有设定当前时间、天气或章节，可在标题下方以小字显示；无设定则不显示
- 进入新地点时自动更新

#### 2.2.2 叙事日志（narrative-log）

- 带垂直滚动条的文本区域
- 按时间顺序追加消息条目
- 每条消息标注角色/来源，如 `GM:`、`玩家:`、`系统:`
- 不添加 emoji，纯文字呈现
- 新消息自动滚动到底部
- 消息类型：
  - GM 场景描述
  - 玩家输入的动作
  - 检定请求与结果
  - NPC 对话
  - 被动技能触发提示
  - 状态变化提示（获得/失去物品、NPC 态度变化等）

#### 2.2.3 输入区

- 单行或少量行文本输入框
- 提示文字：`我想说/想做...`
- 发送按钮
- 支持回车发送
- 输入框上方不放固定快捷按钮（侦察/调查放到右侧面板角色卡附近）

### 2.3 左侧面板：当前场景上下文

左侧面板显示玩家角色当前能感知到的事物，定位为"你已注意到的事物"，不是可交互白名单。玩家仍可输入面板未列出动作。

#### 2.3.1 当前地点

- 地点名称
- 点击地点名称：弹出地点详细描述框

#### 2.3.2 人物

- 当前在场的 NPC 列表
- 每个 NPC 显示：名称 + 简短身份
- 点击 NPC：弹出描述框，显示完整介绍、当前状态、可见信息
- 描述框内可继续输入与该 NPC 相关的动作

#### 2.3.3 物品

- 当前地点中可见的物品列表
- 点击物品：弹出描述框，显示物品描述、主人（若有）、是否可拾取/偷窃

#### 2.3.4 出口

- 当前地点可通往的其他地点
- 点击出口：弹出描述框，显示出口描述，或自动在输入框填入移动动作草稿

#### 2.3.5 队伍成员 / 当前任务

- 保留占位，后续扩展

### 2.4 右侧面板：完整角色卡

右侧面板展示完整角色信息：

- 头像、名称、种族、职业、等级
- 属性值（力量、敏捷、体质、智力、感知、魅力）
- 技能列表（可点击发起检定）
- 豁免检定
- HP / AC / 先攻 / 速度
- 背包
- 法术位和已知法术

#### 2.4.1 侦察 / 调查快捷按钮

在角色卡附近放置两个常用检定按钮：

- **侦察**：触发感知（Perception）检定，查看周围环境
- **调查**：触发调查（Investigation）检定，仔细检查某个区域或物品

点击后系统自动发送对应动作并掷骰。

### 2.5 拖拽把手

- 保留左/右面板的拖拽调整宽度
- 宽度持久化到 localStorage
- 恢复时保证中央区域最小宽度

## 3. 交互模型

### 3.1 核心循环

```
GM 描述当前场景
    ↓
玩家阅读后在输入框输入动作
    ↓
后端意图识别（对玩家透明）
    ↓
规则引擎判断是否需要检定、目标是否合法
    ↓
后端自动掷骰
    ↓
AI GM / 真人 GM 根据结果生成叙事回复
    ↓
更新世界状态（物品、NPC、玩家状态）
    ↓
叙事日志追加结果
```

### 3.2 玩家输入示例

```
GM：石丘旅馆的大厅里壁炉噼啪作响。托布拉·石丘正在吧台后擦杯子，
    弗雷达·矿工坐在角落。吧台后面挂着一串客房钥匙。

玩家：我想趁托布拉不注意，偷走那把钥匙串。

系统：请进行巧手（Sleight of Hand）检定，难度 12。

[后端自动掷骰：d20 + 加值 = 14]

GM：你借着桌子的掩护，手指轻巧地勾住了钥匙串。托布拉仍在擦杯子，
    完全没有注意到。你获得了：客房钥匙串。
```

### 3.3 输入辅助

左侧面板的 NPC、物品、出口可点击，点击后弹出详细描述框。当前阶段不实现"点击后自动填充输入框"的快速选择功能，后续可扩展。

### 4.2 可见信息

- 地点描述、NPC、物品、出口默认对进入该地点的玩家可见
- 不单独设置"显眼物品"分类

### 4.3 隐藏信息

- 由 `hidden` 字段定义
- 需要玩家主动侦察/调查，或被动技能满足 DC 才能发现
- 剧本未写隐藏信息时，不硬加

### 4.4 场景节点

- 预置的触发式叙事片段
- 当玩家满足触发条件时，GM 叙事中自然插入
- 用于控制剧情节奏和关键信息释放

## 5. NPC 系统

### 5.1 NPC 数据

NPC 需要足够完整的设定，AI 才能保持一致发挥：

```jsonc
{
  "toblen-stonehill": {
    "id": "toblen-stonehill",
    "name": "托布拉·石丘",
    "race": "矮人",
    "role": "旅馆老板",
    "description": "一位面容和蔼的矮人旅馆老板...",
    "personality": ["谨慎", "好客", "护短"],
    "goals": ["保护旅馆和家人", "赚足够的钱"],
    "fears": ["红标帮", "失去旅馆"],
    "secrets": ["他其实藏了一把魔法匕首在吧台下面"],
    "passive_perception": 12,
    "passive_insight": 10,
    "attitude": "neutral",
    "attentiveness": "normal",
    "reactions": {
      "theft_detected": {
        "mild": "“嘿，朋友，那东西不属于你。”",
        "severe": "他抄起木棍，大声呼喊守卫。",
        "after_calm": "如果你归还并道歉，他可能会原谅你。"
      }
    },
    "delayed_reactions": [
      {
        "trigger": "item_stolen_from_self",
        "notice_probability": 0.6,
        "notice_after": { "min": 10, "max": 30, "unit": "minutes" },
        "reaction": "他发现钥匙串不见了，开始回忆最后见到的人。"
      }
    ],
    "dialogue": {
      "greeting": "欢迎来到石丘旅馆！来杯麦酒暖暖身子？",
      "rumors": ["听说红标帮最近收敛了不少..."]
    }
  }
}
```

### 5.2 NPC 状态

运行时 NPC 维护以下状态：

```js
{
  awareness: "unaware",    // unaware | suspicious | alert | hostile
  attitude: "neutral",     // friendly | neutral | hostile
  current_location: "stonehill-inn-hall",
  can_see_player: true,
  memory: [
    { event: "theft_attempt_detected", timestamp: 123456 }
  ]
}
```

### 5.3 NPC 反应流程

1. 玩家动作触发 NPC 相关事件
2. 规则引擎根据事件类型、NPC 性格、当前状态选择反应模板级别
3. AI GM 在模板基础上根据性格、记忆、当前情境润色
4. 更新 NPC 状态

### 5.4 延迟发现

偷窃成功后，根据物品显眼程度和 NPC 细心程度决定是否延迟发现：

- `notice_chance` 决定是否最终会发现
- `notice_after` 决定发现时间范围
- 发现后触发新的 NPC 反应事件
- 若剧本未写，默认不延迟发现

## 6. 玩家角色与技能

### 6.1 角色卡

右侧面板展示完整角色卡，数据来自 `localStorage.currentCharacter` 或后端角色数据。

### 6.2 常用检定

角色卡附近放置两个最常用检定按钮：

- **侦察**：发起感知（Perception）检定
- **调查**：发起调查（Investigation）检定

所有技能检定也可通过角色卡中的技能列表点击触发。

### 6.3 被动技能

当玩家进入地点或发生事件时，后端自动用被动技能比对隐藏信息 DC：

- 被动察觉 ≥ DC：自动发现，GM 叙事中追加
- 被动洞悉 ≥ DC：自动察觉 NPC 隐瞒或说谎
- 被动调查 ≥ DC：自动发现异常装置或机关

被动发现的结果以简洁方式插入叙事，避免叙事过于碎片化。

## 7. AI GM 架构

### 7.1 模式

支持三种模式，可在冒险过程中切换：

| 模式 | 说明 | 当前状态 |
|------|------|----------|
| 单人 AI 模式 | AI 完全主持，无真人 GM | **已实现**，接入 DeepSeek-V4-Flash |
| AI 辅助 GM 模式 | 真人 GM 在线，玩家输入先到 GM 面板，AI 生成建议回复，GM 可一键采用或修改 | 待实现 |
| 纯真人 GM 模式 | AI 只负责状态管理和检定，回复完全由真人 GM 撰写 | 待实现 |

当前单人 AI 模式实现细节：

- **模型**：`deepseek-v4-flash`
- **API 端点**：`https://api.deepseek.com/v1`（兼容 OpenAI ChatCompletions）
- **配置文件**：`backend/.env` 中配置 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`、`DEEPSEEK_BASE_URL`
- **实现文件**：`backend/services/ai_gm.py`
- **调用方式**：两次 AI 调用
  1. `interpret()`：解析玩家输入为结构化意图（intent、target_id、target_type、needs_check、skill、suggested_dc、narrative_description）
  2. `narrate()`：根据规则引擎执行结果生成自然语言叙事
- **降级机制**：AI 调用失败或输出无法解析时，回退到规则引擎模板回复

### 7.2 AI 约束

通过以下方式防止 AI 幻觉：

1. **System prompt 硬约束**：只能根据提供的上下文生成回复，禁止引入未提及的 NPC、地点、物品、剧情。
2. **上下文只包含当前相关数据**：当前地点、在场 NPC、当前章节概要、最近 N 轮对话、玩家角色卡关键信息。
3. **剧本分章读取**：只把当前章节内容和必要的前置背景喂给 AI，禁止 AI 读取后续章节。
4. **地点/章节边界检查**：若玩家试图前往未解锁地点或触发跨章剧情，GM 应拒绝或引导回当前场景。
5. **AI 输出为自然语言**：不强制结构化输出，保持叙事自由感；但规则引擎会从中提取可识别的动作意图和状态变化建议。
6. **场景描述即存在**：场景描述（scene_text）中明确提到的具体物品、NPC、地点均视为真实存在、可交互；未明确点名且不在可见列表中的目标视为不存在。隐藏物品（`visible: false`）需通过侦察/调查等检定发现后才进入可见列表。

### 7.3 规则引擎

AI 负责叙事生成，后端规则引擎负责校验：

- 目标是否存在
- 动作是否允许
- 是否需要检定
- 检定 DC 是多少
- 掷骰结果
- 状态变化是否合法

规则引擎发现 AI 越界时，只采纳合法部分，过滤非法部分。

### 7.4 状态持久化

当前开发阶段使用**内存会话存储**，会话 ID 由后端生成并通过 API 返回给前端：

- 运行时状态保存在 `GameState` 实例中（`backend/services/game_state.py`）
- 状态变更由 `StateManager` 统一执行（`backend/services/state_manager.py`）
- 每次动作返回 `updates` 字段，前端根据它刷新 UI

后续将补充持久化：

- `data/adventures/{adventure_id}/sessions/session-{id}.json`：地点物品、NPC 状态、玩家背包、任务进度、事件队列
- `data/adventures/{adventure_id}/sessions/session-{id}-log.md`：叙事日志与 GM 笔记，作为后续 AI 加载的上下文

### 7.5 骰子

- 后端实现自动掷骰引擎
- 支持 `1d20+4`、`2d6`、`8d6` 等表达式
- 支持优势/劣势
- 前端先不做动画，后续补充

  │
  ├─ 渲染界面

  │   ├─ 左侧面板：当前地点 NPC / 物品 / 出口

  │
  └─ 玩家输入
      ├─ 前端追加玩家输入到 narrative-log
      ├─ POST /api/game/action
      │   ├─ AI GM 解析意图
      │   ├─ 规则引擎校验目标、自动掷骰、生成状态变更建议
      │   ├─ 状态变更系统应用变更
      │   └─ AI GM 生成叙事回复
      │
      ├─ 后端返回 { gm_text, intent, checks, state_changes, updates }
      ├─ 前端追加 GM 回复到 narrative-log
      ├─ 根据 state_changes / updates 更新本地状态与 UI
      └─ 清空输入框

## 11. 设计决策记录

| 决策 | 原因 |
|------|------|
| 取消 7×7 网格导航 | 网格导航更像单机探索游戏，限制了玩家自由宣告动作 |
| 采用 narrative-log + 输入框 | 更贴近线下跑团 GM-玩家对话循环 |
| 左侧面板只显示可见 NPC/物品/出口 | 提供上下文，但不限制玩家自由发挥 |
| 隐藏信息由剧本决定，不硬加 | 避免无意义填充，保证叙事质量 |
| AI 输出自然语言，规则引擎校验 | 保留叙事自由感，同时防止幻觉和非法状态变化 |
| 剧本分章读取 | 控制 AI 上下文范围，防止剧透和跨章跳跃 |
| 不强制结构化输出 | 自由叙事更符合跑团氛围 |
| 偷窃延迟发现由数据驱动 | 在真实感和可控性之间取得平衡 |
| 场景描述中明确提到的物品视为存在 | 贴合线下跑团高自由度，避免 AI 否认场景内可交互对象 |
